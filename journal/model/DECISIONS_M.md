# Model-stream decisions (M-D###)

- M-D001 **Own implementation, no tokenizer library.** DESIGN.md section 3 says "Byte-level BPE from scratch" and allows HF `tokenizers` only as a sanity cross-check. The HF library is not installed and not used. The spec PDF (Term Project.pdf) is not in the repo, so the from-scratch rule is taken from DESIGN.md section 0 (tokenizer and Transformer from scratch, no `nn.MultiheadAttention`, no `scaled_dot_product_attention`, no pretrained weights).
- M-D002 **Id layout:** 0 `<|pad|>`, 1 `<|bos|>`, 2 `<|eos|>`, 3..258 the raw bytes, 259.. merges. Specials first so the pad id is 0. DESIGN lists exactly these three specials. `<|bos|>` is reserved but unused in pretraining.
- M-D003 **No `<|unk|>`.** A byte-level vocabulary has no out-of-vocabulary input, so an unk token would never be produced.
- M-D004 **Pre-tokenisation:** GPT-2 regex (contractions, letters, digits, symbols, whitespace) via the `regex` package, already a project dependency. The pattern is stored in the tokenizer file and checked on load.
- M-D005 **Exact byte round trip.** Input is decoded with `surrogateescape` before the regex and re-encoded afterwards, so invalid UTF-8 survives `encode_bytes` / `decode_bytes` unchanged. Text round trip is exact for any str without lone surrogates.
- M-D006 **Deterministic training.** Word-frequency counts, word types sorted, heap ordered by (-count, pair), so ties go to the smaller pair. Incremental pair counts with a lazy heap (DESIGN section 12 asks for this). Two runs give byte-identical files.
- M-D007 **`min_frequency` defaults to 2 for real corpora**, so singleton pairs are never merged. The mock corpus is too small for 4096 entries at 2 (3386 reached), so the smoke test and tests pass `min_frequency=1` (exactly 4096). The real run must check that vocab 4096 is reached and log the stop point if not.
- M-D008 **Train-only guard** looks at the file *name* (and at each file inside a directory), split into alphanumeric words, and refuses `val, valid, validation, dev, test, heldout, holdout`. Parent directories are not checked on purpose: pytest tmp dirs and `tests/` would trip it. Consequence: a val file named e.g. `part2.txt` is not caught, so the real run should pass explicit train file names.
- M-D009 **Corpus file format (provisional):** `.txt` with documents separated by a form feed, or `.jsonl` with a `text` field, or a directory of either. The data stream has not fixed a format yet; only `read_documents` needs to change.
- M-D010 **Mock corpus:** I did not reuse `slm/data/mock_text.py`. It needs the generation pipeline's validator, cues and plans, which are being changed by the other agent. Instead `tests/fixtures/make_mock_corpus.py` writes a seeded 200-document corpus (`mock_corpus_train.txt`, about 220 KB). Invented names are built from syllables so the word-type count is high enough to reach 4096.
- M-D011 **Model per DESIGN section 4:** learned absolute positions, pre-LN, final LN, GELU MLP with d_ff = 4 d_model, dropout 0.1, tied embeddings, biases on all linears. 6 layers, 6 heads, d_model 384, context 512, vocab 4096 gives **12,417,024** parameters (DESIGN says about 12.4M).
- M-D012 **Init:** N(0, 0.02) everywhere, W_O and the MLP output projection scaled by 1/sqrt(2 n_layer), biases zero.
- M-D013 **Mask:** a fixed lower-triangular buffer (not saved in checkpoints) combined with `doc_ids[:, :, None] == doc_ids[:, None, :]`, so packing is handled inside attention. Masked scores use `-inf`; softmax runs in fp32 and is cast back, which keeps bf16 stable.
- M-D014 **Labels are pre-aligned.** `labels[t]` is the target of the prediction at position t, with -100 ignored. The model does not shift. Packing creates the labels, so masking of padding and cross-document targets lives in one place.
- M-D015 **Packing:** documents are tokens plus `<|eos|>`, never split across sequences, first-fit decreasing (deterministic), pad = 0, doc id 0 for padding. A document longer than 512 tokens is cut into independent 512-token chunks and counted in `n_split_docs` (DESIGN section 2.2 caps documents at about 450 tokens, so this should not happen). The last token of each document (`<|eos|>`) has no label, and the first token of a document is never a target (no `<|bos|>` is prepended).
- M-D016 **Epoch order** depends only on (seed, epoch) through a `torch.Generator`. The packing itself is fixed for a corpus, so every sequence, hence every token, is seen exactly once per epoch, which is what DESIGN section 5 needs for exact exposure.
- M-D017 **Checkpoint format:** `{"config": dict, "state_dict": ...}` loadable with `weights_only=True` (CPU grader requirement, DESIGN section 9).
- M-D018 **Test layout:** new tests live in `tests/model_stream/` (own `conftest.py` registering `slow` and `gpu`, auto-skipping `gpu` without CUDA), so `pyproject.toml` is untouched and does not conflict with the main checkout's uncommitted edits.
- M-D019 **GPU smoke batch size 32** (16,384 positions per step, DESIGN section 5). Measured peak memory is 4.6 GB at 32, 9.0 GB at 64, 13.4 GB at 96 (15.9 GB card), so up to about 96 fits.
- M-D020 **`torch.compile` not used** (DESIGN D-011: no Triton on native Windows). Tried anyway; it fails with `TritonMissing`, recorded in M-F001.

## M02 decisions
- M-D021 **Manifest format (provisional):** JSON `{"version": 1, "files": {rel_path: {"split": train|val|test, "sha256": hex}}}`, paths relative to the manifest's directory, hash of raw bytes. Documented in docs/SPLIT_MANIFEST.md for the data stream. Fixture files carry `-text` in tests/fixtures/.gitattributes so CRLF conversion cannot change hashes; the tests build their manifest in a temp copy anyway.
- M-D022 **Manifest guard replaces the file-name guard** (supersedes M-D008). `train_tokenizer(manifest)` accepts `train` only; the token cache and training loop accept `train` and `val`; `test` is refused everywhere. A file is refused when unlisted, listed under another split, or when its hash differs. Tests: a val file named `part2.txt` is refused; a tampered train file is refused. The module is `slm/split_manifest.py` (top level) to avoid an import cycle between `slm.tokenizer` and `slm.data_loading`.
- M-D023 **Token cache:** `<key>.ids.npy` (uint16, documents concatenated, each ending in `<|eos|>`), `<key>.offsets.npy`, `<key>.meta.json` (n_docs, n_words, n_tokens, tokens_per_word, share_docs_over_context). Key = sha256(tokenizer merge-table hash : file hashes of the split). A different tokenizer or changed file gives a different key. The data hash recorded in meta.json is the hash of ids+offsets. Statistics are also written to `token_stats.json` per split.
- M-D024 **Weight decay only on nn.Linear weight matrices** (not LayerNorm, not biases, not token/position embeddings). This supersedes DESIGN section 5, which put decay on "2-D matrices including the tied embedding"; the M02 prompt asked for no decay on embeddings. Because the head is tied, the LM head is also undecayed.
- M-D025 **LR schedule:** per optimiser step, linear warmup `(step+1)/warmup` to the peak, then cosine to `min_lr_ratio` (0.1) x peak at the last step. Warmup 200 steps by default; the dry run uses 20 because the mock set has only 13 steps per epoch.
- M-D026 **Run layout:** `runs/<name>/seed<k>/` with config.yaml, meta.json (git commit and dirty flag, tokenizer hash, tokenized-data hash, versions, device), loss.csv (`split,step,epoch,tokens_seen,loss,lr,grad_norm,elapsed_s`; train rows are the mean over the last `log_every` steps, val rows every `val_every` steps and at each epoch end), summary.json, checkpoints/. One seed fixes init, dropout masks and epoch order.
- M-D027 **Checkpoints:** `epoch_<EEE>.pt` at the configured log-spaced epochs (default 1,2,3,5,8,12,16,20, the last epoch always saved), each a normal model checkpoint plus step, epoch, tokens_seen, seed, val_loss and the train config, loadable with `weights_only=True`. `last.pt` (model, optimizer, RNG states, counters; about 3x the size) is rewritten after every epoch.
- M-D028 **Resume at epoch boundaries only.** Restores model, optimizer, torch CPU/CUDA RNG, step, tokens_seen; epoch order depends only on (seed, epoch) so it replays. loss.csv rows beyond the restored step (a crashed partial epoch) are dropped. Test: 4 epochs straight == 2 epochs + resume + 2 epochs, bit-identical weights and CSV on CPU.
- M-D029 **NaN/inf guard:** every step checks the loss and the clipped gradient norm and raises `TrainingAborted` with step, epoch, seed, lr and the last finite loss, plus a hint. The sweep records such runs as `aborted` and excludes them.
- M-D030 **`label_eos` meaning.** The prompt said "eos unlabeled as in M01". In M01 the label at the `<|eos|>` position is masked (its next token belongs to another document) but `<|eos|>` is a *target* for the last word of each document, so the model learns to end documents. I made `label_eos` control that: `True` (default, = M01 behaviour) trains the model to predict `<|eos|>`; `False` masks the target. SFT needs `True` (it must learn to stop). If "unlabeled" was meant to say eos should never be predicted in pretraining, set `label_eos: false`. Flagged for review.
- M-D031 **Validation:** token-weighted mean cross-entropy over the whole val set, fp32, dropout off, same label settings as training.
- M-D032 **ModelScorer boundary:** tokenise prompt and continuation separately and concatenate the ids, after moving one trailing prompt space onto the continuation (`"... is " + "Caldreth"` becomes `"... is" + " Caldreth"`, which equals the joint tokenisation because the GPT-2 pre-tokeniser attaches a space to the next word). Reason: the context must not depend on the continuation being scored (no leakage through merged tokens), and the same value string must give the same tokens under every prompt. Tests: equals a manual log-softmax computation, chain rule `score(p, a+b) = score(p, a) + score(p+a, b)`, first continuation token scored from prompt-only logits, prompt ids unchanged by the continuation.
- M-D033 **ModelScorer details:** returns the sum of natural-log probabilities (`score_details` also gives the token count for length normalisation); no `<|bos|>`/`<|eos|>` added, because the model never saw a bos and never predicts a first token of a document, so an empty prompt raises; an empty continuation scores 0.0; a too-long prompt is cut from the left, a continuation of context-1 tokens or more raises; right padding inside batches is harmless under the causal mask; fp32, eval mode, no grad. It does not import evaluation-stream code.
- M-D034 **Sweep:** grid lr {3e-4, 6e-4, 1e-3} x dropout {0, 0.1, 0.2}, 1 seed, selection by minimum val loss over the scheduled checkpoint epochs; final 3 seeds use the chosen lr/dropout for the full 20 epochs. The best epoch is informational only (docs/HPARAM_PROTOCOL.md).

## M03 decisions
- M-D035 **Weight decay follows DESIGN section 5 (reverses M-D024).** Decay on every 2-D matrix including the tied token embedding; no decay on LayerNorm parameters and biases. The learned position table is also 2-D, so it decays (DESIGN says "2-D matrices"). Reason: DESIGN is authoritative. `TrainConfig.decay_embeddings: false` (configs/train.yaml) restores the M-D024 behaviour. Tests: `test_weight_decay_groups`, `test_weight_decay_flag_restores_old_behaviour`.
- M-D036 **SFT prompt template (DESIGN 7.1):** `Question: <q>\nAnswer:` + ` <one sentence containing the value>` + `<|eos|>`. Prompt and answer are tokenised separately and joined (the answer starts with a space). The builder rebuilds the prompt from `question` and refuses a row whose own `prompt` differs.
- M-D037 **SFT batches and loss.** One example per row, right-padded to the longest in the batch (`doc_ids` 1 for tokens, 0 for padding); no packing, because eval prompts start at position 0. Labels are -100 on the prompt, the answer tokens and `<|eos|>` are targets, nothing follows eos. Validation is the token-weighted fp32 mean over those targets.
- M-D038 **Trainer.** AdamW with the pretraining parameter groups, LR 1e-4, 20 warmup steps, cosine to 10%, at most 6 epochs, batch 16, grad clip 1.0, dropout kept from the pretraining checkpoint unless set. Early stopping when sft_val loss has not improved for 2 epochs. Checkpoints: epoch_EEE.pt every epoch, best.pt (lowest val loss), last.pt (resume state, epoch boundaries). Seed k starts from the highest-numbered epoch checkpoint of pretraining seed k. DESIGN gives LR and epochs; batch, warmup length and patience are mine (configs/sft.yaml).
- M-D039 **Decoder.** Plain recompute loop, argmax (ties to the lowest id), stop at `<|eos|>` (not emitted) or at a token containing a newline (kept; the evaluator cuts the text at the first newline), at most 48 new tokens (DESIGN 7.2). The prompt is cut from the LEFT to `context_len - max_new_tokens` tokens so generation never slides; `Generation.truncated_prompt` and `n_dropped` report it. `doc_ids` is all ones. Optional seeded temperature and top-k sampling (`generate_ids`) for qualitative samples; temperature 0 is greedy.
- M-D040 **Exact match.** DESIGN names no normalisation, so: cut at the first newline, strip, collapse whitespace runs to one space, case-sensitive, nothing else. `exact_match` = normalised prediction equals the normalised gold ANSWER SENTENCE (DESIGN 7.4 lists "exact value match" and "contains-match" separately; with sentence answers the strict reading is sentence equality). `contains_value` (value string occurs in the prediction) is a separate column and is never mixed into exact_match. The comparison table calls it `contains_gold`.
- M-D041 **Test-access ledger.** `slm.guard.open_split(manifest, split, purpose)` is the only reader of test files: `SplitManifest.read_verified` refuses `test` unless a context variable set by the guard is on. Each test read appends a JSON line (timestamp, split, purpose, git commit and dirty flag, caller, manifest, file hashes) to `reports/test_access_log.jsonl` before the bytes are read; train/val reads are not logged; unlisted, mis-split or hash-mismatched files are refused. Pre-registered rule in docs/HPARAM_PROTOCOL.md section 6.
- M-D042 **Before/after QA (7b).** `compare_checkpoints` evaluates any checkpoint (pretrained or SFT) on the same rows with the same template and decoding, asserts identical question ids, and `comparison_table` gives checkpoint | eval_set | n | exact_match | contains_gold. Recorded as asked via the M01 session, which relayed that the user assigned it to M03; it is not in my own copy of the prompt.
